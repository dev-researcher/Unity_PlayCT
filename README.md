# Unity_PlayCT

Unity project for Meta Quest 3 VR research (stationary interaction, no locomotion).

- Unity: 6000.0.84f1 (Unity 6 LTS). Install the Android Build Support module (OpenJDK, Android SDK & NDK Tools).
- XR: OpenXR (Meta Quest Support feature, Android build target) + XR Interaction Toolkit 3.4.1.
- Render pipeline: Built-in, Vulkan, IL2CPP, ARM64.
- Scene: `Assets/Scenes/Laboratory.unity` (4 m x 4 m university laboratory: oak table, bookshelf, cabinet, window with daylight, XR Origin at room centre).

## Research infrastructure

`Assets/Scripts/Research` is shared by every task.

- `SessionManager` holds session ID, participant ID and condition. Set them in the inspector or in `session_config.json` inside `Application.persistentDataPath` (`{"participantId":"P012","condition":"PreAdapted","hanoiDiskCount":4}`).
- `EventLogger` appends one JSON object per line to `<persistentDataPath>/PlayCT/<sessionId>/events.jsonl`. Every line carries `session_id, participant_id, condition, task, event, timestamp_utc, t_session_s` followed by the task's own fields. Tasks implement no logging of their own; they send a `ResearchEvent` to the logger.
- `ConditionManager` gives a typed view (`Static` or `PreAdapted`) of the SessionManager's condition text; the legacy value `baseline` is read as `Static`. Any other text is invalid and the experiment will not start.
- `IExperimentTask` is what a task exposes to the experiment: `TaskId`, `StartTask(condition)`, `IsRunning`, `IsCompleted`, `Completed`, `EndTask(reason)`. `HanoiTask` implements it; a future task does the same and registers itself with `TaskOrchestrator` (inspector `tasks` list or `Register`).
- `TaskOrchestrator` runs the task IDs in its `taskSequence` list (in the Laboratory scene `Hanoi`, `CuboRelaciones`, `GabineteFormas`, then `ElCorreo`) one after another and logs `experiment_started`, `task_started`, `task_ended`, `task_skipped` and `experiment_ended` (task name `Experiment`) to the same `events.jsonl`. Sequence logic lives in the pure class `ExperimentSequencer`. In the Laboratory scene the orchestrator starts Hanoi, so `HanoiTask.beginOnStart` is off there.

On Quest the folder is `/sdcard/Android/data/<package>/files/PlayCT/`.

## Tower of Hanoi (`Assets/Scripts/Tasks/Hanoi`)

The `Hanoi_Task` object in `Laboratory.unity` holds a wooden board with pegs `Origen`, `Apoyo`, `Destino` and five oak disks. Disks are picked up with XR Interaction Toolkit direct interactors on both controllers. The participant sees no counter, timer, score, solution or error text.

- Number of disks: 3, 4 or 5 (`HanoiTask.diskCount`, `SessionManager.hanoiDiskCount`, or `HanoiTask.Configure(n, condition)`). Optimal moves (7 / 15 / 31) are only used in the logged metrics.
- A release is accepted only over a peg; a larger disk on a smaller one, or a release away from the pegs, sends the disk back to its slot (animated).
- Events per trial: `trial_started`, `disk_grab`, `disk_release` (disk_id, source_peg, destination_peg, legal, outcome, move_number, resulting_state, completion_status), `trial_completed`, `trial_summary` (completion time, total moves, invalid attempts, efficiency = optimal / moves, move sequence, attempt sequence). A summary is also written as `hanoi_trial_NN_summary.json` next to the event log.
- Completion is detected when every disk is on `Destino`; the task then locks and raises `HanoiTask.TrialCompleted`.

## Cubo de Relaciones (`Assets/Scripts/Tasks/Cubo`)

The `Cubo_Task` object in `Laboratory.unity` builds, when it runs, a 38 cm cube of 27 dark-oak cubies with six matte sticker colours (Up linen, Down ochre, Front sage, Back slate, Left clay, Right plum) in the middle of the table. It implements `IExperimentTask` (`TaskId` `CuboRelaciones`); the orchestrator starts it after Hanoi, and while it runs it switches off `Hanoi_Task` so the table is clear (restored when the task ends).

- Interaction: one hand grips the cube by its body or edges to stabilize it (it never moves); the other hand grips the middle of a face and lets go. A short movement selects the face; a clear twist around the face centre asks for a quarter turn clockwise or counterclockwise as seen from outside. Only exact 90 degree turns of a face layer exist, so there is no free rotation. Turns that are not in the trial's allowed set, or attempted without the stabilizing hand, are refused: the cube does not move, the attempt is logged, and the participant continues. Nothing is displayed to the participant.
- Logic (`Logic/`, no Unity types): `CubeState` (54 stickers, immutable, deterministic quarter turns), `CubeMove`, `CuboTrialConfig` (mini-task, initial state, goal, allowed rotations, duration), `CuboTrial` (rules, events, metrics), `CuboSummary`. A trial is configured through `CuboTrialSpec` entries (`CuboTask.trials` in the inspector); an empty list uses `CuboProtocol.Default()`.
- Mini-tasks, none of which asks for a full solve: `cruz_clara` (form a single-colour cross on a face), `corregir_una_pieza` (undo one displaced layer using only three faces), `elegir_una_secuencia` (choose which allowed turns undo a three-turn change), `que_permanece` (after turning, touch the face whose nine stickers did not change). Each trial has an optional time limit that only ends the trial; no timer is shown.
- Events (task `CuboRelaciones`): `trial_started`, `stabilizer_changed`, `face_selected`, `rotation` (selected_face, rotation_axis, rotation_direction, rotation_amount_deg, legal, outcome, move_number, previous_state, resulting_state), `face_answer`, `trial_completed`, `trial_summary`. A summary per trial is also written as `cubo_trial_NN_summary.json`. The condition is recorded in every event and summary and does not change the rules.

## Gabinete de Formas (`Assets/Scripts/Tasks/Gabinete`)

The `Gabinete_Task` object in `Laboratory.unity` builds, when it runs, a wooden fitting cabinet on the table: a dark-oak board with one recessed opening per shape (lined in slate) and a linen tray in front holding the pieces, which are oak. It implements `IExperimentTask` (`TaskId` `GabineteFormas`); the orchestrator starts it after Cubo, and while it runs it switches off `Hanoi_Task` (restored when the task ends). The task manages only its own trials; it never starts or ends the session.

- Shapes: prism, cylinder, truncated cone, wedge, L-shaped block and hexagonal piece, plus a half cylinder and a T-shaped block that exist only so the 8-shape configuration has eight different pieces. Each opening is the exact footprint of its piece with 4% clearance. Prism and L-block start turned 90 degrees from the orientation their opening accepts (the hexagon 30 degrees); the cylinder and truncated cone (whose openings differ in size and taper) fit at any yaw, the prism after a half turn, the hexagon every 60 degrees.
- Interaction: each piece is an `XRGrabInteractable` that tracks position and rotation. When released, its pose in board space goes to the logic. Over an opening it is a placement attempt: it is accepted only if the opening belongs to that piece, the piece is upright, within `positionTolerance` of the opening centre and within `orientationTolerance` of an accepted yaw (folded by the shape's symmetry). Nothing snaps the piece to an opening beforehand; an accepted piece is only lowered into the opening it already matches. A rejected piece (and one released away from the openings) returns to its tray slot in its starting orientation. Nothing is displayed to the participant: no messages, hints or highlights. Pieces can be placed in any order and there is no move-order rule.
- Logic (`Logic/`, no Unity types): `GabineteShapes` (catalog and symmetry), `GabineteTrialConfig`/`GabineteTrialSpec`/`GabineteProtocol` (configurations), `GabineteTrial` (state, rules, events, metrics), `GabineteSummary`, and pure mesh geometry (`PolygonTriangulator`, `GabineteMeshBuilder`). `GabineteTask.trials` in the inspector takes `GabineteTrialSpec` entries (shape count 4, 6 or 8, or an explicit shape list, tray slots, start yaws, duration); an empty list uses `GabineteProtocol.Default()` (4, 6 and 8 shapes). Tolerances are in `GabineteTask.rules` and are placeholders until calibrated in headset.
- Events (task `GabineteFormas`): `trial_started`, `piece_picked_up`, `piece_released` (off-target releases), `placement_attempt` (piece_id, piece_type, target_opening, attempted_opening, attempted_opening_type, starting_orientation_deg, attempted_orientation_deg, orientation_error_deg, position_offset_m, placement_result, valid, completed_pieces, resulting_state), `trial_completed`, `trial_summary`. A summary per trial is also written as `gabinete_trial_NN_summary.json` (placement attempts, valid and invalid attempts by reason, off-target releases, rotation count, completion time, placement and action sequences). The condition is recorded in every event and summary and does not change the rules.

## El Correo (`Assets/Scripts/Tasks/Correo`)

The near-transfer task. The `Correo_Task` object in `Laboratory.unity` builds, when it runs, a wooden postal map on the table: a dark-oak board with five turned-oak settlements A to E, linen strips for the directed paths (an arrowhead at the destination end and one ink slot per unit of capacity, plus the capacity written beside it), the existing Origen and Destino plaques next to A and E, and three parcels (P1 taller, terracotta and tied with a linen band because it is the high-priority one; P2 and P3 plain). Two wooden buttons, Enviar and Limpiar, sit at the front edge. It implements `IExperimentTask` (`TaskId` `ElCorreo`); the orchestrator starts it after Gabinete, and while it runs it switches off `Hanoi_Task` (restored when the task ends). It never starts or ends the session, and the rules are identical under Static and PreAdapted.

- Network (fixed in `CorreoNetwork.Standard`, not configurable): A>B 2, A>C 1, B>D 2, C>D 1, C>E 2, D>E 1. There is no B>C path. All three packages start at A and must reach E.
- Shipment: one action with a source, a destination and one or more packages, moved together. Refused, in this order, when: there is no such path (`no_path`); no package is selected (`no_packages`); a package is not at the source (`package_not_at_source`); more packages than the path capacity (`capacity_exceeded`); P1 and P3 travel together (`p1_p3_shared`); the shipment would leave P1 in D (`p1_waiting_in_d`); a low-priority package would reach E before P1 has (`priority_violation`). A refused shipment changes nothing and nothing is moved for the participant.
- Interpretations to confirm with the researchers: a shipment is one hop, so nothing can carry P1 on from D within the same action; "P1 cannot wait in D" is therefore implemented as any shipment whose resulting state has P1 in D is refused, and P1 has to go by way of C (A>C, C>E). A consequence: P1 sent to B can never leave B (B>D is refused), so that trial cannot be completed. "P1 reaches E no later than P2 and P3, counted in shipments" is enforced when a shipment would deliver P2 or P3 to E while P1 is not at E and not in that same shipment (arriving together counts as equal and is allowed). "P3 cannot share a shipment/path with P1" is implemented as the shipment only.
- Interaction: touching a settlement chooses the source (first touch), then the destination (second touch); touching the source again clears both, touching the destination again clears it. Touching a parcel adds it to the shipment (it lifts) or removes it. Enviar confirms; Limpiar clears the selection. A shipment with an incomplete selection attempts nothing. After Enviar the selection is cleared; an accepted shipment carries the parcels along the path, a refused one only gives the parcels a brief sideways nudge. Nothing else is displayed: no messages, hints, scores or timers.
- Logic (`Logic/`, no Unity types): `CorreoNetwork`, `CorreoState` (immutable package locations, shipment count and the shipment in which each package reached E), `CorreoRules` (the verdict for a shipment), `CorreoTrial` (selection, shipments, events, metrics), `CorreoSummary`, `CorreoTrialConfig`/`CorreoTrialSpec`/`CorreoProtocol` (only the duration is configurable; the default protocol is one trial of 600 s).
- Events (task `ElCorreo`): `trial_started`, `selection_changed`, `confirm_ignored`, `shipment_attempt` (source, destination, selected_packages, selected_count, path_capacity, legal, outcome, rejection_category, shipment_number, delivered_packages, locations_before, locations_after, completion_status), `trial_completed`, `trial_summary`, `trial_reset` (researcher/test operation `CorreoTrial.Reset()`, which returns the trial to the initial state; participants have no control for it). `legal` and `outcome` follow Hanoi and Cubo. A summary per trial is also written as `correo_trial_NN_summary.json` (attempts, valid and invalid shipments, rejections by category, final locations, the shipment in which and the time at which each package reached E, whether the priority constraint held, completion time, shipment and action sequences).

## Guide / help (`Assets/Scripts/Research/Guide`)

One guide for every task. `GuideEngine` (pure logic) watches the events the orchestrator and the tasks already write (`task_started`, `trial_started`, `trial_summary`, `task_ended`), so no task calls it. It speaks at five moments: task start, trial start, help request, trial end and task end (only when the task was completed). `GuideDirector` connects it to the `EventLogger` (it subscribes to `EventLogged`); `GuidePlaqueView` is the physical face: a linen card in an oak stand at the far edge of the table and a wooden Ayuda button (an `XRSimpleInteractable`, so the existing XR interactors press it). Nothing floats in the participant's view.

- Messages are Spanish questions (`GuideCatalog.Common` and each task's `*ResearchProfile.Guide()`); they ask what the participant sees, what constraint applies, what changes and what stays the same. They never name a move, a piece, an answer, a score or a reward, and tests check every message for that (each ends with "?", unique IDs, no instruction or judgement words).
- Per task, a `GuideProfile` sets which moments are active (`Disable`), its own messages for each moment (the standard ones are used otherwise), `HelpRequestsEnabled`, `HelpCooldownSeconds` (default 15 s) and `MaxHelpPerTrial` (0 = no limit). Choice is deterministic: each moment cycles through its messages in order. Help is answered only while a trial is running; every request is logged even when refused.
- Events (task = the active task): `guide_shown` (guide_type = `task_start|trial_start|help_request|trial_end|task_end`, message_id, text, trial_index, sequence) and `guide_help_requested` (answered, result). They go to `events.jsonl` with the usual envelope (session, participant, condition, task, timestamp).
- The four tasks' guide and metric configuration lives in `Tasks/*/Logic/*ResearchProfile.cs`; `Research/Catalog/ResearchTaskCatalog.cs` is the one list to extend for a new task.

## Data aggregation and CSV export (`Assets/Scripts/Research/Data`)

`SessionDataExporter` (scene object `SessionDataExporter`) reads the session's `events.jsonl` back, aggregates it and writes CSV next to it when the orchestrator finishes or aborts the experiment (or when `Export()` is called). It only reads: `events.jsonl` and the per-trial summary JSON files are not changed.

- Raw events -> `LoggedEvent` (`EventLogReader`, tolerant of bad lines, which are counted) -> `TrialRecord` per task trial -> `SessionSummary`. The `trial_summary` events the tasks already log are the source; if a task logged none for a trial, a record is built from its lifecycle events (`record_source` = `task_events`). A record has session, participant, condition, task, trial, start/end time, duration, completion, attempts, valid and invalid actions, moves, efficiency and the action sequence, plus the task's own fields (`TaskSpecific`). Fields a task does not log stay empty; nothing is invented.
- `ITaskMetricsAdapter` maps a task's summary field names onto the common model (`MappedTaskMetricsAdapter`); a task without an adapter still gets records through `GenericTaskMetricsAdapter`.
- `session_summary.csv`: one row per task trial. The first 18 columns are fixed (`session_id, participant_id, condition, task_id, trial, start_time, end_time, duration, completed, completion_status, completion_time_s, attempts, valid_actions, invalid_actions, moves, efficiency, action_sequence, record_source`; `duration` is in seconds), followed by one `TaskId.field` column per task-specific metric declared by the adapters, so the header does not depend on which tasks ran. Not-applicable values are empty cells. `events.csv` (optional, `exportEventsCsv`): one row per event with the envelope and the remaining fields as one JSON cell.
- Format: RFC 4180 quoting, CRLF, UTF-8 without BOM, invariant numbers (`.` decimal), ISO 8601 UTC times, `true/false`; same events give the same bytes. Files go in `<persistentDataPath>/PlayCT/<sessionId>/`.

## PC / Quest Link

Quest 3 stays the primary target. The Android configuration in `Assets/XR` is untouched. A Standalone entry was added next to it in `XRGeneralSettingsPerBuildTarget.asset` (OpenXR loader, initialize on start) and `OpenXRPackageSettings.asset` (Oculus Touch Controller and Meta Quest Touch Plus profiles enabled), so Play Mode in the Editor and a Windows build use OpenXR through Meta Quest Link. There is no second task implementation: the tasks are the same `XRGrabInteractable`/`XRSimpleInteractable` scripts and no platform code (`Assets/Scripts` has no `UNITY_ANDROID` or `UNITY_STANDALONE` branches). The repository has no desktop or keyboard/mouse input adapter, and none was added; without a headset use the XR Interaction Toolkit XR Device Simulator sample.

Not verifiable without opening Unity (nothing here was opened in Unity): that Unity accepts the hand-written Standalone assets as they are (it may rewrite them and add the remaining OpenXR features for Standalone on first open), that Meta Quest Link is set as the active OpenXR runtime on the PC (Meta Horizon Link app > Settings > General > OpenXR Runtime), that controller input and the Ayuda button work over Link, that the Windows graphics API default (Direct3D 11 is fine; only Android is pinned, to Vulkan) renders the lab correctly, and that Windows IL2CPP/Mono builds succeed.

## Tests

- Unity Test Runner: `Assets/Tests/EditMode` (pure logic, log format, mesh geometry) and `Assets/Tests/PlayMode` (Laboratory scene driven through the task).
- Without the Editor: `dotnet test Tools~/OffEngineTests` (.NET 8 SDK) runs the EditMode tests plus the real `HanoiTask`/`HanoiDisk`/`CuboTask`/`GabineteTask`/`CorreoTask`/`TaskOrchestrator`/`EventLogger` scripts on a small fake engine (356 tests). It complements, and does not replace, Play Mode.

## Opening the project on a new machine

1. Install Unity Hub and Unity **6000.0.84f1** (the repository root is the Unity project folder) with the modules for your platform. For Quest builds add **Android Build Support** including OpenJDK and Android SDK & NDK Tools.
2. Clone the repository and add the folder in Unity Hub. On first open Unity resolves `Packages/manifest.json`, creates `Library/` and `Packages/packages-lock.json` (commit the lock file after the first successful open), and may ask to import TextMeshPro essentials; accept.
3. Open `Assets/Scenes/Laboratory.unity` and press Play. Without a headset the XR Origin does not move; use the XR Device Simulator or connect the Quest (Meta Horizon Link / Air Link); OpenXR is already configured for the Standalone platform (see "PC / Quest Link" below).
4. Quest build: switch platform to Android; OpenXR with Meta Quest Support and the Touch controller profiles is already configured for Android in `Assets/XR`.
